# MemState: why it is a proof of concept, and how it aligns with the GEM paper

Paper: *Is Agent Memory a Database? Rethinking Data Foundations for Long-Term AI Agent Memory* (arXiv:2605.26252v1, see [`2605.26252v1.md`](2605.26252v1.md)).
Repo: <https://github.com/CoDS-GCS/MemState>, commit `945d7c4`, cloned to `../../MemState/`.

**Method.** Everything below comes from reading the source and the repo's own `docs/`. Nothing was executed when this was written (`kuzu` was not yet installed), so runtime behavior is `[INFERENCE]` from code; facts since reproduced by runs are in [`../findings.md`](../findings.md). File and line references are to `../../MemState/src/memstate/`.

## 1. What "proof of concept, not full implementation" means

The README header says *"It is Proof-of-Concept, NOT Full Implementation"* and the About section says it is *"a runnable proof-of-concept that demonstrates how the core ideas of GEM work in practice"* whose *"design will continue to evolve as the framework is extended beyond this initial reference build."* The paper makes the same claim from its side: §4.3 calls MemState *"a feasibility sketch on a property-graph substrate"* and *"a compatibility layer, not a native expression of GEM"*.

There are two different gaps, and they should not be conflated:

| Gap | Whose claim | Meaning |
|---|---|---|
| **Substrate gap** | The paper (§4.3, §5) | GEM is reconstructed on generic Kuzu primitives. A native engine would store field histories as bitemporal attributes, put propagation semantics on edges, compile policy postconditions into the commit protocol, etc. The paper calls these *research directions*, not implementation gaps. |
| **Feature gap** | The repo (docs + code) | Parts of the GEM design that the paper describes as realized, or realizable on Kuzu, are not implemented in the repo. Its own docs mark several as *Planned*. |

This document is about the second gap, measured against what the paper says §4 MemState does.

### What the repo is

- Python 3.11+ package `memstate` (`pyproject.toml`): FastAPI service, embedded Kuzu store, Ollama/Groq LLM chat with memory tools, MCP server, D3 graph-explorer UI.
- Core layering (from the docstrings "Block 1 façade", `store/graph_store.py:61`, and "Block 2 — validated transitions into GraphStore", `core/executor.py:49`): `GraphStore` (Kuzu persistence) → `Executor` (ingest and query) → `Reasoner` (background maintenance, "v1: rule-based only", `reasoner/engine.py`).
- HTTP surface: `POST /v1/ingest`, `POST /v1/query`, each followed by a FastAPI `BackgroundTask` that calls `Reasoner.run(...)` (`api/main.py:136-165`). Revise and forget have no public route.
- Test suite: 39 test functions across 6 files (`tests/`). By file name they cover field history tools, topic fields, Study ingest, text chunking, agent visualization and system context. None targets revise, forget or the Reasoner by file name; I did not read the test bodies.

## 2. Alignment with the paper's data model $M_t = (D_t, S_t, P_t)$

| Paper element | Repo realization | Status |
|---|---|---|
| **Topic** as self-contained semantic unit: title, summary, dense embedding, fields with value histories (§4.1) | Kuzu `Topic` node with `title`, `summary`, `embedding`, `fields_json`, `salience`, `failed_salience`, `archived`, `topic_kind`, `topic_history_json` (`schema.py`, `datamodel/constants.py`). Each field is a `TopicField` with `field_type`, `ref_topic_id`, `salience` and a newest-first `history` list (`datamodel/fields.py`). | **Aligned** |
| Field history $H_{i,j}=\langle(v,t,\pi)\rangle$, updates append (§4.1) | `append_field_history` inserts at index 0 (`store/graph_store.py:436-472`). `FieldHistoryEntry` carries `value`, `valid_from` (t), `provenance` (π), plus `why_changed`, `impact_expected`, `operation`. | **Aligned** |
| Default read returns only $v_k$ (C1); temporal queries return history | `TopicField.current_entry()` is `history[0]`. `Executor._field_bundle` returns history only when the `temporal` stage is requested and `explain` is set (`core/executor.py:230-274`). | **Aligned** |
| Revision promotes a subset of fields into a standalone topic (*Alice* example, Fig. 3) | `promote_fields_to_nested_topic` and `undo_promote_nested_topic` in the store (`graph_store.py:538`, `:659`), exposed as LLM tools. Triggered by the LLM or a user, not by a "enough interactions reference her" rule. | **Partial** (mechanism yes, trigger no) |
| $S_t$ with two typed edge kinds: **extension** (entailment, propagates) and **association** (no propagation) | One Kuzu rel table `RELATED(kind STRING)` (`store/kuzu_adapter.py:87`). `kind` is a free-form string. A grep for `extension` and `association` across all `.py` files returns no matches. | **Not implemented** |
| $P_t$ as declarative ⟨event, condition, action⟩ rules living inside $M_t$ (Def. 3, Listing 1) | `Policies` is a plain Pydantic `BaseModel` (not env-configurable) with 6 numeric knobs: `max_field_history`, `max_topics_for_forget_scan`, `forget_salience_threshold`, `topic_count_soft_limit`, `query_salience_bump`, `embedding_dimension` (`core/models.py:8-19`). `default_policies()` returns `Policies()` (`core/policies.py`). No event/condition/action structure, not stored in the graph, no `POLICY` syntax. | **Not implemented** (a parameter set, not a policy language) |

## 3. Alignment with the four operators

### Ingestion (§3.2, §4.2)

- **Paper:** LLM picks a host topic from titles and summaries, reads the schema, appends the new value to an existing or new field, refreshes the embedding, flags extension-linked topics for revision.
- **Repo:** `Executor.ingest` supports three placements: `new_topic`, `extend_topic`, `version_field` (`core/executor.py:84-228`). Each appends field history and refreshes the topic embedding. Optional `suggest_similar` returns kNN topic ids as hints.
- **Where the LLM sits:** the `Executor` does not choose a host topic. The *caller* supplies `placement` and `topic_id`. The LLM-driven selection lives in the chat layer, which calls `memory_*` tools (`llm/tools_schema.py`, `llm/tool_runner.py`) and the two-phase Study pipeline for long documents (`llm/study_hierarchy.py`).
- **Missing:** no "flag extension-linked topics for revision" step (there is no extension edge, see §2).
- **Verdict:** **Partial.** C1 and C4-style append-only history are real. Integration into the right host is delegated to the LLM and caller.

### Revision (§3.2, §4.2)

- **Paper:** detects duplicate topics, conflicting field values, schema drift and dependency inconsistencies; walks extension edges; marks superseded values with provenance.
- **Repo:** only the first of those. `run_revise_duplicates` merges topic pairs whose titles are exactly equal and non-empty, capped at 50 pairs per run (`executor.py:346-350`, `graph_store.py:1236-1290`). `merge_topics` rewires `RELATED` edges, copies fields that exist only on the dropped topic, then `DETACH DELETE`s it (`graph_store.py:1249-1290`). The survivor is the lexicographically smaller uuid (`a.id < b.id`), not the older or newer topic. The dropped topic's summary, salience, topic history and embedding are lost. Pair selection ignores `archived`, so an active topic can be merged into an archived one and then vanish from `/v1/query`. Despite `revision.html`'s 'periodic schedule', no code emits `cron`, so revise runs only after `/v1/ingest`.
- **The repo's own docs confirm the limits** (`docs/operations/revision.html`): *Field history merge for same-name fields: Planned. Semantic duplicate detection (summary + embedding): Planned. Conflict reconciliation across fields (not just duplicates): Planned.* Name collisions *"are left untouched on the surviving topic"*, so the dropped topic's history for a shared field name is **discarded** on merge.
- **No dependency propagation (C3):** nothing walks edges after an update.
- **Verdict:** **Minimal.** One heuristic out of the four evidence types.

### Forgetting (§3.2, §4.2)

- **Paper:** per-field salience that rises on access and **decays on disuse**; three thresholds $\theta_{summary}$, $\theta_{remove}$, $\theta_{archive}$ (ordered as a graded ladder [INFERENCE: the paper does not state the inequality]) giving compress → hide → archive.
- **Repo:** one rung. `run_forget_low_salience` sets `archived=True` and halves salience for any active topic whose salience is `< forget_salience_threshold` (default 0.05) (`executor.py:353-362`). Archived topics are filtered out of the embedding/forget scans and out of every `/v1/query` (`graph_store.py:1103-1104`, `:954-955`, `executor.py:307-308`).
- **No decay exists.** A grep for `decay` and `theta` across the Python sources in `src/` returns no matches (the only hits are D3 layout code in `api/static/ui/app.js`). Nothing lowers salience over time. Topic salience rises through the `/v1/query` bump (+0.1, capped at 1e9, `executor.py:329-331`). Field salience rises through the chat read bump (capped at `field_salience_max=10`, `graph_store.py:209`). Otherwise salience is set explicitly (default `1.0` on creation, or by an LLM/UI call). It is also overwritten with the average field salience on every field write (`graph_store.py:214-218`), and forget halves it (`executor.py:360`).
- **Consequence [INFERENCE]:** with default `salience=1.0` and no decay, a topic's salience cannot fall below 0.05 on its own. Archiving needs two things. First, something must lower salience explicitly: `memory_update_topic` (which the `retention_trim` guidance prompts the LLM to call), UI `PATCH`, or a `/v1/ingest` `new_topic` with a low `salience` and no fields, since field writes reset salience to the field average. Second, the Reasoner's forget scan must run, which happens only at ≥ 500 topics because `cron`/`memory_pressure` are never emitted. The other route is setting `archived=true` directly via UI `PATCH` or `memory_update_topic`.
- **The repo's own docs confirm** (`docs/operations/forget.html`): *Summarize: Planned. Detach: Planned. Archive: Shipped.* and *"Forget decisions today look at salience only — not recency or semantic redundancy."* (The same page's `cron` schedule and `max_topics_for_forget_scan` scan bound have no counterpart in the code.)
- **Granularity:** the paper wants sub-unit (field) granularity. Forget here acts on whole topics; field salience exists on the model but is not used as an archival criterion.
- **Verdict:** **Minimal.** Archive rung only; the salience-decays-on-disuse mechanism that makes it "relevance-driven" is absent.

### Retrieval (§3.2, §4.2)

- **Paper:** routes the query to topic-based, temporal or structural mode; every accessed unit's salience increases (C6).
- **Repo:** `Executor.query` takes `stages` (`semantic`, `temporal`, `structural`) and returns `TopicBundle`s with kNN similarity, neighbors and field bundles (`executor.py:276-344`). For every returned topic it adds `query_salience_bump` (0.1) to topic salience and appends a `salience` event to `topic_history_json` (`:328-339`).
- **Chat path:** `MemoryToolRunner._bump_read_access_salience` bumps **field** salience after read tools, but only when the chat intent router classified the turn as `query` or `both` (`llm/tool_runner.py:273-282`; `store/graph_store.py:191-212`). `GraphStore.bump_field_salience_on_query` then sets topic salience to the field average.
- **Weak spots [INFERENCE from code, not run]:**
  1. The `/v1/query` bump touches **topic** salience only, not field salience.
  2. `append_field_history`, `update_field`, `set_field_ref` and `delete_field` all call `sync_topic_salience_from_fields` (`graph_store.py:214-218`), which overwrites topic salience with the average field salience (fields default to 1.0). Any later field write therefore erases `/v1/query` bumps and any low salience set at ingest. For example, five queries take salience to 1.5, and one `version_field` resets it to 1.0.
  3. The routing is a similarity search, not the paper's title/summary → schema → field-values LLM walk; that walk is again the chat layer's job.
  4. Topics created through the UI (`POST /api/ui/topics`) or the LLM tool `memory_create_topic` are stored with no embedding (`ui_api.py:133`, `tool_runner.py:468`), so `/v1/query` semantic search never returns them until a `/v1/ingest` `extend_topic`/`version_field` refreshes the embedding. The `salience` returned in each `TopicBundle` is the value before this query's bump (`executor.py:315` vs `:328-331`).
- **Verdict:** **Partial.** The read-as-write idea is present in both paths; the two paths update different salience levels.

## 4. Alignment with the six correctness conditions

The paper (§4) says the data model gives **C1, C3, C4 by construction**, lifts **C2** to a data-model guarantee, and the operators supply **C5, C6** *under transitions*.

| Cond. | Paper's claim for MemState | What the code does | Verdict |
|---|---|---|---|
| **C1** Query soundness | By construction | Default read returns `history[0]` (newest); history only on explicit temporal request. | **Holds** at the field level. |
| **C2** Transition soundness | Policy postconditions checked before atomic commit; violating transitions rejected (Alg. 1, line 12) | No policy evaluation anywhere. Grep for `commit`, `rollback`, `BEGIN TRANSACTION` in `src/` finds nothing. Each store call runs its own Cypher; an ingest touching several fields is several independent writes. `Policies` values are read as thresholds, never as postconditions. | **Not implemented** |
| **C3** Dependency consistency | By construction via typed extension edges | No extension edge type, no propagation on update. | **Not implemented** |
| **C4** Provenance preservation | By construction | Entries carry `provenance`, `why_changed`, `valid_from`. But (a) history is truncated to `max_field_history` (500, newest kept) in `append_field_history`; (b) `merge_topics` discards the dropped topic's same-name field history; (c) `delete_field`, `delete_topic`, and the LLM tools `memory_delete_field` / `memory_delete_topic` are destructive. | **Holds for the append path; broken by bounded history, merge and delete.** |
| **C5** Bounded active state ($\lvert D_t^{active}\rvert \le \beta(n)$) | Salience-driven archiving, recoverable | `topic_count_soft_limit` (500, archived topics included in the count) only gates *whether the forget scan runs*; it is not a cap. `max_topics_for_forget_scan` is defined but never read. Archived topics are never returned by `/v1/query`. They can be recovered via `GET /api/ui/topics/{id}`, listed via `GET /api/ui/topics?include_archived=true` or the LLM tool `memory_list_topics`, and un-archived via `PATCH`. Without decay (see §3), and with `cron`/`memory_pressure` never emitted, the scan archives little. | **Partial** (mechanism exists, bound not enforced) |
| **C6** Retrieval-induced adaptation ("repeated retrieval **strictly reduces** eligibility for attenuation") | Salience increment in the retrieve branch | Salience increments on read. Without decay, the increment cannot be shown to change eligibility, and the query/write interaction in §3 can erase it. | **Partial** |

## 5. Summary

| GEM component | Paper (§4) | Repo |
|---|---|---|
| Topics, field histories, embeddings on Kuzu | Realized | **Yes** |
| Append-only versioned fields, default-current read | Realized | **Yes** |
| Ingestion operator | LLM host-topic selection + flag dependents | Placement API + LLM tools; no flagging |
| Revision operator | 4 evidence types, edge walk | Exact-title duplicate merge only |
| Forgetting operator | 3-rung ladder, decaying salience | Archive rung only, no decay |
| Retrieval operator | 3 modes, salience increment | Similarity query + salience bump (topic-level in API, field-level in chat) |
| Extension vs association edges, C3 propagation | Realized | **No** (single free-text `RELATED.kind`) |
| Declarative ⟨event, condition, action⟩ policies, commit-time check, C2 | Realized | **No** (numeric config only) |
| Atomic transition commit | Alg. 1, line 12 | **No** |

So the repo implements the **data model half** of GEM (topics + field histories + salience + embeddings) and the **plumbing** (API, UI, LLM tooling) that the paper does not describe. It implements the **governance half** (typed propagation, policy language, commit-time checks, graded decaying forgetting) only in skeletal or planned form. That is consistent with the paper's own framing of MemState as a feasibility sketch, but it means the paper's sentence "C1, C2, and C4 hold by construction" is only true for C1 and, on the append path, C4. C2 is not enforced in this repository.

## 6. What this means for the review demo

> **Superseded as the demo plan** by [report §9](../report/gem-limitations-and-directions.md#9-demo-a-gem-conformance-suite). This section is kept as the code-reading analysis the demo design grew from.

Demonstrable today, with the repo as is:

1. **Failure ② fix (semantic revision):** ingest `Deadline: March 15`, then `version_field` with `April 20`; default query returns April 20, temporal+explain query returns both with provenance. (C1, C4.)
2. **Failure ① (growth):** show the exact-title duplicate merge via the Reasoner after `/v1/ingest`. It runs as a background task, so poll before asserting. The survivor is the lexicographically smaller id, and any pre-existing or archived topic with the same title also takes part.
3. **Failure ④ (read-only retrieval):** query the same `/v1/ingest`-created topic repeatedly and show salience rising (topic-level, `/v1/query`). Each response shows the pre-bump value. The `query_bump` events are visible in `topic_history` via `GET /api/ui/topics/{id}`. Do no field write in between, because it resets salience to the field average.
4. **Failure ③ (forgetting), archive rung only, with conditions:** the Reasoner runs forget only when `count_topics()` ≥ `topic_count_soft_limit` (500, archived topics included). No code emits `cron` or `memory_pressure` (`reasoner/engine.py:33-40`, `api/main.py:146,162`). So first seed ≥ 500 topics. Then create a topic via `/v1/ingest` `new_topic` with `salience=0.01` and **no fields**: any field write resets topic salience to the average of its field saliences, which default to 1.0 (`graph_store.py:471,214-218`). Then send any `/v1/ingest` or `/v1/query`, and the background Reasoner archives the topic and halves its salience. The alternative is `PATCH /api/ui/topics/{id}` with `{"archived": true}`, which archives directly and bypasses the Reasoner and the threshold. An archived topic never appears in `/v1/query`, not even with `topic_ids` (`executor.py:307-308`). It stays readable via `GET /api/ui/topics/{id}` and can be restored with `PATCH {"archived": false}`.

Not demonstrable without extending the repo (candidates for the demo's own code, kept honest as "beyond the PoC"):

- Salience **decay** so forgetting is driven by disuse, and a three-rung ladder.
- **Extension edges** plus propagation on `field_updated` (Listing 1).
- A **policy postcondition check** wrapped around each transition (C2).
- Unifying field-level and topic-level salience bumps so the API and chat paths agree.
- A history-preserving merge (C4).

When presenting, label items 1–4 as "what MemState implements" and the second list as "what the paper claims and the PoC leaves open".

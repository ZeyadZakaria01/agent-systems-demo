# 21: Verdict rules and per-probe date detection

**What to build:** The verdict rules the build settled with the user, and the time-probe scoring that follows from them. A verdict rests only on the cases that could run, and its cell says how many were skipped; a row with no case that could run is not-scored. Each time probe gets two cells, "accepts dates" and "answers correctly given dates", with per-probe date detection (today the adapter requires both `valid_from` and `invalid_at` for any date to be sent). A probe is `absent` when a needed date is not accepted and `fail` when it is accepted and answered wrong. Spec: user stories 36, 71, 72, 78; Implementation Decisions "Verdict model", "Time-probe stories", "Time-probe scoring", "System adapter"; tickets "Ratify verdict rules set during the build" (items 2, 4, 5) and "Close the suite audit's design gaps" (items 3, 4); ADR 0002.

**Blocked by:** 09 (time probes)

**Status:** ready-for-agent

- [ ] `Verdict.from_cases` rests on the cases that could run; a case that needs another condition's capability is n/a; the scorecard cell reads `pass (n case(s) n/a)` when cases were skipped; no case could run → `not-scored`. The `absent` / `not-scored` difference is documented in the module and tested. (The build already does this; the spec wording now matches.)
- [ ] `describe()["accepts"]` reports `valid_from`, `invalid_at`, `valid_at`, `recorded_at` separately. For MemState each flag is read from the server's OpenAPI schema over all schemas (`valid_from` and `invalid_at` on any write model, `valid_at` and `recorded_at` on any query model); in-process systems declare theirs. The both-required rule at `demo/memstate_system.py:97-102` is removed.
- [ ] Each time probe lists the dates it needs (T1, T2, T3, T6: `valid_from`; T4: `valid_from` and `invalid_at`; T5: `valid_from`, `valid_at` and `recorded_at`). A system receives the writes with the dates it accepts; a system that accepts none of a probe's needed dates gets the same writes undated and every asked date is answered with the same plain read.
- [ ] Per probe, cell 1 "accepts dates" is yes, no or partly, with the schema probe as evidence. Cell 2 is `pass` (every asked date right and, on the patch, history intact), `fail` (the dates are accepted and an answer is wrong, labelled over-blocking when the control date fails) or `absent` (a needed date is not accepted). Upstream reads absent on all six probes (F19) and is never called wrong.
- [ ] T5 is `absent` only when `recorded_at` is not accepted. When it is accepted and both answers are identical, the probe scores `fail` (`demo/checks/time_probes.py:138-164` changed). The F19 evidence (the same answer to both questions on upstream) stays as the absence evidence.
- [ ] T4 story 2 gains the ask Oct 15 → $100 ("a plain statement ends the override"); upstream's last-write answer is $100 (correct by recency). `demo/time_stories.py` and the shifted-story test are updated.
- [ ] The adapter refuses the newest-entry fallback for a system whose `accepts` shows any date: a field read without `current` raises an error instead of reading `history[0]` (`demo/memstate_system.py:54-64`). Undated systems keep the fallback.
- [ ] Suite tests, in-process with stand-in systems (no MemState mock): a start-date-only system gets dates for T1, T2, T3, T6 and is absent on T4 and T5; an end-date-capable system with a wrong answer reads fail; a `recorded_at`-accepting system with identical answers reads fail on T5; a stand-in with no dates reads absent on all six.
- [ ] Smoke run: a recorded upstream run prints all six probes with both cells; every probe is absent with the schema evidence and no verdict reads "fail". Any departure from "Expected verdicts" is logged in `docs/journal.md`.

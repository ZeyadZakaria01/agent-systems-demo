# 26: Reference GEM, phase 1

**What to build:** Our own in-process system, built to the paper's definitions of C1–C6 behind the system adapter, on the kindest reading of Definition 4 (ADR 0007). It is expected [INFERENCE] to pass the C1–C6 checks, pass the time probes that need only a start date (T1, T2, T3, T6) and be absent on T4 (no end date) and T5 (no recorded time). It is built against the stricter checks and the pre-registered expectations, which are already in the spec. Spec: user stories 58–63, 70; Implementation Decisions "Reference GEM", "Expected verdicts"; ticket "Reference GEM design" (all items).

**Blocked by:** 22 (revised checks), 24 (stricter C3 and C2(c)), 25 (C4′ probe)

**Status:** resolved

- [x] `demo/systems/reference_gem.py` implements the adapter in-process, with no server and no LLM. Topics with fields; entries with value, provenance, the stored source message and one timestamp (when the value became true); extension and association edges; policies; per-topic salience, last touch and archived flag. Each ingest and each query is one interaction.
- [x] **Phase 1 reading of Definition 4:** the current value is the entry with the latest timestamp not after the asked date, among non-archived entries. No end date and no recorded time: `describe()["accepts"]` is true for `valid_from` only.
- [x] **Policies:** ⟨event, condition, action⟩ rules stored in the state as data and addable at runtime through `add_policy`. Conditions come from the fixed vocabulary (field comparisons on the topic being written; "a neighbour exists via an extension or association edge"). Actions: reject (a postcondition checked against the proposed next state before commit) and flag for revision. A default policy rejects empty and null values. A transition commits all or nothing.
- [x] **C3 as the Listing 1 policy, one hop, undirected** (C3's own wording, `2605.26252v1.md:212`, `:275`): an update flags every topic connected to the updated one by an extension edge, whatever the edge's direction, with evidence (`{updated_field, timestamp}`); association edges never flag; the flag clears when the flagged topic is next written, and that write flags its own neighbours. No repair.
- [x] **History:** capped at 500 entries; overflow is archived, not deleted, and readable by id. A valid value that is archived reads as no current value plus a note that an archived value exists. Every write stores its source message; `resolve_source` returns it.
- [x] **Salience and forgetting reuse MemState's code wherever it has the behaviour:** θ_archive 0.05; +0.1 per returned topic; **halve salience when a topic is archived** (`MemState/src/memstate/core/executor.py:360`; new); declared β = 500 active topics (MemState's `topic_count_soft_limit`), reported by `describe()`. **Added because the paper requires it and the code lacks it:** decay on disuse per interaction (`2605.26252v1.md:323`; MemState's `docs/operations/forget.html` describes decay but its code has none, F10, F24), λ = 0.05^(1/400) (an untouched topic at 1.0 falls below θ after 400 interactions), computed lazily; and a forgetting check after every interaction. Any read or write of a topic resets its decay clock.
- [x] **C6:** +0.1 per returned topic, as-of reads included; retrieval is MiniLM brute-force top 8.
- [x] **Merge (revision)** runs after every ingest, as MemState's Reasoner does (`MemState/src/memstate/reasoner/engine.py:36-37`), as a separate step after the write commits; the survivor keeps both histories with their provenance; the current value is the later write. Until revision has run, a read can see both copies.
- [x] C6 clause 2 seeds the target and the control at 0.06 on this system, a declared per-system test setting (upstream keeps 0.03 and 0.01; a seed below θ would be archived by its own interaction). The constants and this setting are recorded in the deviations table and the report's declared-simplifications list, before the first scored run.
- [x] Suite tests, in-process, pin the phase 1 column of "Expected verdicts" (C1–C6 rows pass; T1, T2, T3, T6 pass; T4 and T5 absent; C4′ pass) and the observations: reinforcement precision 1/8 on the storyline; about 400 active topics at 2,000 ingests against β = 500. A departure from the pre-registered column is logged in `docs/journal.md` and reported, and the expectation is not rewritten.

Departures (none changes the pre-registered column; details in `docs/journal.md`):
- `describe()["accepts"]` is `valid_from` and `valid_at`, not `valid_from` only: the asked date of Definition 4's reading is `valid_at`; without it the probes' control dates are plain reads and T1-T3, T6 fail.
- Entries carry `expired_at: None` (the probes' history check wants the key).
- New `describe()["c6_clause_2_seeds"]` (default `None`); C6-2 reads until the first forgetting pass when the seed is at or above θ.
- `triage._increment` counts only rises (decay is not a negative increment).
- Decay: a touch materialises the decayed value and restarts the count; a write adds nothing, a retrieval adds 0.1 (journal).
- Merge deletes the dropped topic (as MemState does) after copying its entries, tagged `operation: "merged"`, `merged_from_topic_id`, to the survivor (lowest id); archived topics are never merged. A write to an archived topic is stored and leaves it archived (C4's forgetting case writes to a topic archived by its own interaction).
- C3 flags on a write of fields to an existing topic (Listing 1's `field_updated`), not on creation; a flag clears on the next write of fields to the flagged topic.
- Seams for ticket 29's mutants: `_cap`, `_bump`, `_effective`, `_apply_policies`, `_neighbours`/`_holds`, `_resolve_source`, `_propose`; `revise_after_ingest=False` shows both copies until `revise()` (ticket 30's merge window).
- Later tickets: the windows are in `interactions` (`ReferenceGem.interactions`); register the system in `systems.py` (ticket 30); phase 2 adds a mode to the same class (`_valid_entry`, `Entry.view`, `describe`).

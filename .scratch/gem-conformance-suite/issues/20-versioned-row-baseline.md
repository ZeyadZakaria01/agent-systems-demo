# 20: Versioned-row baseline

**What to build:** The baseline becomes a versioned row, replacing the last-write-wins row of ticket 01 (clean cutover, no second baseline). It is MAFBench's concrete solution (versioned fact stores with multi-version concurrency control, write-ahead logging and conflict resolution, `2602.03128v2.md:568`), so "database guarantees are necessary but not sufficient" is tested against what the benchmark asks for. It sits behind the same system adapter, in-process. Expected [INFERENCE]: it gives C1, C2's atomic commit and current-value rule, and C4; it lacks declarative policies (C2(c)), dependency tracking (C3), forgetting (C5) and reinforcement (C6), each scored `absent` and confirmed by a probe. - [x] `demo/systems/baseline.py` is a versioned row: an append-only history per (title, field) with the time each value was recorded, one transaction per write (all fields of a write apply, or none), in-process. The last-write-wins row, its top-10 query and its "no history" behaviour are removed.
- [x] It accepts the ingest shape but **rejects empty and `null` values**, like a NOT NULL / CHECK constraint: the write returns `Rejected` and nothing is saved (the whole write, since a write is one transaction).

It has no salience (reads return none), archived flag, edges or valid-time dates; each missing capability is confirmed by a probe so the rows can read `absent` (ADR 0002). A read returns the latest recorded value and changes nothing.
